# Release 0.10.0: a list that stays fast, and the release build checked on a device — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> Status: not started. Execute on branch `release-0.10.0` from `main` after v0.9.0 is merged and tagged (plans `2026-09-15-release-0.8.0-tags-own-types.md`, `2026-09-15-release-0.9.0-web-settings.md`).
> Chosen by the user on 2026-09-15 from the improvement list (items B4–B6). Findings behind it, from the code at 0.8.0:
> - `ObjectsModel.cardsFor` (feature/objects/ObjectsViewModel.kt) re-runs, for every object, `objectDao().stats(uuid)`, an attachment lookup, a file lookup and `InsightsModel.usage(uuid)` (`activityDao().readingRows`) whenever any reminder or activity changes (`combine(reminderDao().allOpen(), activityDao().version())`), and `totalDue()` runs `stats` again per object with open reminders. `DueListModel.items` (feature/reminders/DueListScreen.kt) does `get`, `stats` and `usage` per object with open reminders. That is 4–5 queries per object per change: fine at 20 objects, a visible stall at a few hundred.
> - CI (`.github/workflows/ci.yml`) runs JVM tests, lint, screenshots, assembles, and the contract test. Nothing runs the minified release APK, and the device tests never run on CI. apexweather's CI has both (`instrumented` on API 31, `release-smoke` on API 34 with `tools/release-smoke.sh`), and its `:baselineprofile` module records startup and journey profiles.

**Goal:** The objects list, the due list and the digest read the mirror in a constant number of queries however many objects there are; CI runs the device tests and a release-APK smoke test on emulators; a baseline profile makes cold start faster, measured.

**Architecture:** Two aggregate DAO queries (per-object stats for all live objects; all readings up to today) and one cover query replace the per-object loops; `ObjectsModel` and `DueListModel` assemble the same `ObjectCard`/`DueItem` values from maps, proven equal to the old per-object result by an equivalence test. CI gains two emulator jobs modelled on apexweather's. A `:baselineprofile` test module (as in apexweather) records the cold start to the server screen and the signed-in tour against a seeded mirror, with a macrobenchmark to measure it.

**Tech Stack:** As 0.9.0, plus `androidx.benchmark` macro 1.5.0-rc02, `androidx.profileinstaller` 1.4.1, the `androidx.baselineprofile` Gradle plugin, `androidx.test.uiautomator`, and `reactivecircus/android-emulator-runner@v2` in CI (versions as apexweather's `gradle/libs.versions.toml` and `ci.yml`).

## Global Constraints

- Results must not change: every `ObjectCard` field and every `DueItem` the aggregate path produces equals what the per-object path produced for the same mirror (equivalence tests below).
- Query budget: `ObjectsModel.allCards()` and `DueListModel.items()` each run at most 4 queries per emission regardless of object count.
- CI emulator jobs: device tests on API 31 (`google_apis`, x86_64), release smoke on API 34; both upload their reports; neither may address anything but the runner's emulator.
- The baseline profile generator needs API 33+ and no root; the profile is committed (`app/src/release/generated/baselineProfiles/…`) so ordinary builds use it without a device.
- No user-visible change; no new permissions; lint `warningsAsErrors`.
- Default version `0.10.0` / `1000`.
- Local runs: Gradle in the foreground (Bash timeout 600000); device work only on an emulator via `adb -s emulator-5554` (a physical phone may be attached); `./gradlew --stop` afterwards.

- [ ] **Step 1: Write the failing equivalence test**

The test seeds an in-memory mirror (`TestDatabase.inMemory()`) with 30 objects in a tree, entries with costs and counter readings (some deleted, some dated in the future), covers (one pointing at a deleted attachment), and open, snoozed, done and reading reminders, then asserts:

```kotlin
    @Test fun `cards from the aggregates equal cards from the per-object queries`() = runBlocking {
        seed(db, objects = 30)
        val today = LocalDate.parse("2026-09-15")
        val expected = legacyCards(db, today)             // the pre-change ObjectsModel code, copied into this test verbatim
        val actual = ObjectsModel(db) { today }.allCards().first()
        assertEquals(expected.sortedBy { it.uuid }, actual.sortedBy { it.uuid })
    }

    @Test fun `due items from the aggregates equal the per-object due items`() = runBlocking {
        seed(db, objects = 30)
        val today = LocalDate.parse("2026-09-15")
        assertEquals(legacyDue(db, today, 30), DueListModel(db) { today }.items(30).first())
        assertEquals(legacyDue(db, today, 7), DueListModel(db) { today }.items(7).first())
    }

    @Test fun `query count does not grow with the number of objects`() = runBlocking {
        val small = countQueries { seed(it, objects = 5); ObjectsModel(it).allCards().first() }
        val large = countQueries { seed(it, objects = 200); ObjectsModel(it).allCards().first() }
        assertEquals(small, large)
        assertTrue(large <= 4, "allCards ran $large queries")
    }
```

`countQueries` builds its own in-memory Room database with `setQueryCallback(RoomDatabase.QueryCallback { sql, _ -> if (sql.trimStart().startsWith("SELECT", ignoreCase = true)) count++ }, Executors.newSingleThreadExecutor())` and counts only the queries issued while computing the one emission (reset the counter after seeding). `legacyCards` and `legacyDue` are the current `cardsFor` and `items` bodies pasted into the test file as private functions — they are the reference, and they are deleted from production code in Step 3.

Run: `./gradlew :app:testDebugUnitTest --tests '*AggregateEquivalenceTest' --console=plain` — the equivalence tests pass against the unchanged code (they compare the reference with itself so far), and the query-count test FAILS (the large seed runs hundreds of queries). That failure is the RED.

- [ ] **Step 2: Aggregate DAO queries**

```kotlin
    /** `stats(uuid)` for every live object at once. */
    @Query(
        """SELECT o.uuid AS objectUuid,
                  COALESCE(SUM(a.cost_cents), 0) AS totalCostCents,
                  COUNT(a.uuid) AS activityCount,
                  MAX(a.counter_value) AS currentCounter,
                  MAX(a.date) AS lastActivityDate,
                  MAX(CASE WHEN a.counter_value IS NOT NULL THEN a.date END) AS lastReadingDate
           FROM objects o LEFT JOIN activities a ON a.object_uuid = o.uuid AND a.deleted_at IS NULL
           WHERE o.deleted_at IS NULL
           GROUP BY o.uuid""",
    )
    suspend fun statsForAll(): List<ObjectStatsRow>
```

```kotlin
    @Query(
        """SELECT object_uuid AS objectUuid, date, counter_value AS counterValue FROM activities
           WHERE deleted_at IS NULL AND counter_value IS NOT NULL AND date <= :upTo
           ORDER BY object_uuid, date, counter_value""",
    )
    suspend fun readingRowsForAll(upTo: String): List<ObjectReadingRow>
```

```kotlin
    @Query(
        """SELECT o.uuid AS objectUuid, f.sha256 AS sha256 FROM objects o
           JOIN attachments t ON t.uuid = o.cover_attachment_uuid AND t.deleted_at IS NULL
           JOIN files f ON f.uuid = t.file_uuid
           WHERE o.deleted_at IS NULL AND f.sha256 != ''""",
    )
    suspend fun coverShas(): List<CoverRow>
```

Check each against the per-object query it replaces (`ObjectDao.stats`: `MAX(date)` over all entries, `lastReadingDate` over entries with a counter; the cover lookup's `takeIf { it.deletedAt == null }` and `takeIf { it.isNotBlank() }`) and match them exactly; the equivalence test is the judge.

- [ ] **Step 3: Assemble from maps**

`InsightsModel`: add `fun usageFrom(rows: List<ObjectReadingRow>, today: LocalDate): Insights.Usage? = Insights.usage(rows.mapNotNull { r -> runCatching { LocalDate.parse(r.date) }.getOrNull()?.let { Insights.Reading(it, r.counterValue) } }, today)` and make `usage(uuid)` delegate to it (one source of truth).

`ObjectsModel.cardsFor(objects)`: inside the existing `combine(...)` block, fetch once — `val stats = db.objectDao().statsForAll().associateBy { it.objectUuid }`, `val readings = db.activityDao().readingRowsForAll(t.plusDays(1).toString()).groupBy { it.objectUuid }`, `val covers = db.attachmentDao().coverShas().associate { it.objectUuid to it.sha256 }` — and build each card from the maps (an object with no row gets zero stats, as `stats(uuid)` returns). `totalDue()` uses `statsForAll()` and `readingRowsForAll` the same way. `DueListModel.items` fetches `objectDao().all().first()` (or the existing live-objects query) once, plus the two aggregates, and builds `DueItem`s from maps. Delete the per-object loops; keep `ObjectDao.stats(uuid)` for the detail screen.

```yaml
  instrumented:
    name: Device tests
```

```kotlin
package dev.logb.android.baselineprofile

import androidx.benchmark.macro.junit4.BaselineProfileRule
import androidx.test.uiautomator.By
import androidx.test.uiautomator.Until
import org.junit.Rule
import org.junit.Test

/**
 * The cold start to the first screen, and nothing else, for the startup profile (it reorders the
 * dex, which only helps when it holds the launch path alone). A fresh install has no server, so
 * the first screen is the server screen: Compose, Hilt, DataStore and the session restore all run.
 *
 * Generate with `./gradlew :app:generateReleaseBaselineProfile` with only an API 33+ emulator
 * attached (`ANDROID_SERIAL=emulator-5554`).
 */
class StartupBaselineProfile {
    @get:Rule val rule = BaselineProfileRule()

    @Test
    fun startup() = rule.collect(packageName = PACKAGE, includeInStartupProfile = true) {
        pressHome()
        startActivityAndWait()
        device.wait(Until.hasObject(By.textContains("Server")), 15_000)
    }

    private companion object { const val PACKAGE = "dev.logb.android" }
}
```

`StartupBenchmark.kt`: apexweather's benchmark with `packageName = "dev.logb.android"` and the same `By.textContains("Server")` wait, `CompilationMode.None()` vs `CompilationMode.Partial()`, 10 cold iterations.
